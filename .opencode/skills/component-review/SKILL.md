# コンポーネントレビュー
指定されたコンポーネントの実装・設計・品質を横断的かつ網羅的にレビューし、問題点と改善提案をまとめた Markdown レポートを**対象コンポーネントのディレクトリー直下**に出力します。

## 1. 対象の特定手順
1. 指定されたコンポーネント名から、リポジトリ内の対象ディレクトリーを特定します。
2. ディレクトリーが直ちに特定できない場合は、リポジトリ内を検索して候補を確認します。
3. **複数の候補があり一意に特定できない場合は、推測で進めず必ずユーザーに確認してください。**

## 2. レビュー方針
* **局所分析に留めない:** 対象コンポーネント単体だけでなく、必要に応じてリポジトリ全体を調査します。
* **横断的比較:** 同様の役割を持つ類似コンポーネントを確認し、プロジェクト全体の設計方針や実装パターンを把握します。
* **文脈の尊重:** 既存実装と異なることだけを理由に問題視してはいけません。コンポーネント固有の仕様による意図的な差異である可能性を必ず検証します。

## 3. レビュー手順

### Step 1: プロジェクトガイドラインの確認
以下のファイルを優先的に確認し、対象コンポーネントに適用すべきルールを把握します。
* `AGENTS.md` / `SKILL.md`（エージェント向け指示）
* `README.md` / `CONTRIBUTING.md`
* コーディング規約
* TypeScript / JavaScript 設定 (`tsconfig.json` 等)
* Lint / Formatter 設定 (`.eslintrc`, `.prettierrc` 等)
* テスト設定 (`jest.config.js`, `vitest.config.ts` 等)

### Step 2: コンポーネント構造の把握
対象ディレクトリー配下の関連ファイルを一通り確認します。
* コンポーネント本体 / 型定義 (`.types.ts` 等)
* カスタム Hooks / Context / ユーティリティ
* テスト (`.test.ts`, `.spec.ts`) / Storybook (`.stories.ts`)
* スタイル (`.css`, `.module.css` 等) / ドキュメント

### Step 3: 類似コンポーネントとの横断比較
同種コンポーネントと比較し、以下の要素について一貫性と妥当性を確認します。
* API 設計（Props 名、型名、イベント名、デフォルト値）
* 状態管理・Context・エラーハンドリングのパターン
* アクセシビリティ対応およびテスト構成の同一性
* そのコンポーネントだけに存在する特異な実装の必要性

### Step 4: 多角的な実装レビュー
以下の10項目について詳細なチェックを行います。

| レビュー項目 | チェックポイント |
| :--- | :--- |
| **1. バグ・実装上の問題** | 条件分岐の誤り / `null`・`undefined` 処理 / 境界値 / 状態更新の不整合 / イベント・非同期処理 / DOM操作 / Reactライフサイクル・再レンダリング / Controlled・Uncontrolled の扱い / SSR・CSR 互換性 |
| **2. 型安全性** | 不要な `any` / 不適切な型アサーション・型ガード / ジェネリクスの誤用 / public API の型設計 / 型で表現可能な制約の実装保証漏れ |
| **3. 規約遵守** | 命名規則 / ファイル構成 / `import` 順序 / コードスタイル / JSDoc・コメントの正確性 |
| **4. デッドコード** | 未使用の `import`・型・関数・変数 / 到達不能コード / 不要な Props・分岐・ユーティリティ<br>※**CSS クラス名はデッドコードレビューの対象外**とします。 |
| **5. 誤字脱字 (Typos)** | コメント / JSDoc / エラーメッセージ / UI テキスト / `aria-*` 属性値 / 識別子名（型・変数・関数名） |
| **6. アクセシビリティ** | WAI-ARIA 準拠 / `role`・`label` / フォーカス管理・キーボード操作 / セマンティック HTML / スクリーンリーダー対応 / 状態属性 (`aria-disabled` 等) |
| **7. テスト** | カバレッジ（主要挙動・境界値・異常系） / ブラウザ特有挙動のテスト / 実装詳細ではなく「振る舞い」を検証できているか |
| **8. パフォーマンス** | 不要な再レンダリング・計算・DOM操作 / Context 肥大化<br>※`useMemo`/`useCallback` 不在のみを理由に指摘せず、実際のコストと影響度を評価すること。 |
| **9. 保守性・設計** | 過度な複雑性・重複 / 責務の集中 / 不自然な抽象化 / 誤用を招く API 設計 |
| **10. ドキュメント整合性** | JSDoc・Storybook・仕様記述と実際の実装との不一致 |

## 4. 指摘事項の検証・評価基準

### 指摘の妥当性検証
問題を報告する前に、必ず以下の6点を確認してください。
1. **問題の確実性:** 実際に問題が存在するか。
2. **影響度:** 具体的にどのような不具合・害をもたらすか。
3. **発生条件:** どういったシチュエーションで発生するか。
4. **意図の有無:** 既存仕様や設計意図で正当化されないか。
5. **他との整合性:** 類似コンポーネントと比較した結果どうであるか。
6. **解決策:** 具体的かつ実現可能な改善策があるか。

> **注意事項**
> * 推測に基づく指摘を「確定した問題」として記載してはいけません。仕様上判断できない事項は「確認事項・懸念点」に記載してください。
> * 個人の好みや単なるスタイルの違いを「問題」として報告してはいけません。

### 重要度の判定基準
* `重大`: 重大なバグ・セキュリティリスク等、早急な修正が必須の問題
* `高`: 動作不良や将来的な重大設計崩壊につながる可能性が高い問題
* `中`: 品質・保守性・一貫性を明確に向上させる改善点
* `低`: 軽微な改善点や細かな規約違反

## 5. 出力フォーマット

レビュー対象ディレクトリーの直下に Markdown 形式で出力します。

* **ファイル名:** `<component-directory>/review.md`
* **競合回避:** すでに同名ファイルが存在する場合は上書きせず、`review-20260918.md` など適切な別名を使用してください。

### テンプレート

```markdown
# <Component Name> レビュー

## 概要
レビューの全体概要および総評を簡潔に記述します。

## 調査結果

### 1. [高] <問題のタイトルを簡潔に記述>

- **ファイル:** `path/to/file.ts`
- **場所:** `L10-L20`
- **抜粋:** `<抜粋コード (複数行に渡る抜粋の際は複数行表示する)>`

#### 問題点
発生している問題の具体的な内容。

#### 理由
問題である理由、発生条件、およびシステムへ与える具体的影響。

#### 提案
修正案・改善コードの提案。

### 2. [中] <次の問題のタイトル>

...

## 確認事項・懸念点
問題として断定はできないが、仕様確認や将来的な検討のために共有しておくべき事項・懸念点。

```

※ `調査結果` は重要度（`重大` → `高` → `中` → `低`）の順に並べてください。同一原因による重複指摘はまとめて記述します。

## 6. 制約事項

1. **コードの非破壊原則:** レビュー対象のソースコード、テストファイル、設定ファイル、ドキュメント、スタイル等を**一切変更してはなりません**。
2. **変更許可範囲:** 本 SKILL において変更・生成が許可されるのは、**レビュー結果を出力する Markdown ファイルのみ**です。
3. **作業領域のクリーンアップ:** レビューに伴い生成された一時ファイル（ビルドキャッシュやログ等）は、完了時に必ず削除してください。

## 7. 完了チェックリスト

出力を作成後、タスクを完了する前に必ず以下のチェックリストを全件確認してください。

* [ ] 対象コンポーネントおよびディレクトリーを正しく特定した。
* [ ] プロジェクトのコーディング規約・設定ガイドラインを確認した。
* [ ] 類似コンポーネントとの横断比較を行った。
* [ ] 10個の観点（バグ、型安全性、CSS以外のデッドコード、誤字、テスト、a11y、React/パフォーマンス、保守性、ドキュメント整合性）を検証した。
* [ ] 各指摘に具体的な根拠（ファイルパス・行番号・発生条件・影響度）を提示した。
* [ ] 指摘事項に適切な重要度を設定した。
* [ ] 具体的で実現可能な改善案を記載した。
* [ ] 対象コードおよび既存ファイルを一切変更していないことを確認した。
* [ ] 対象ディレクトリー直下に規定フォーマットで Markdown レポートを出力した。
